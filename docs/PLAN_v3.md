## 1. نظرة عامة

نظام سحابي متعدد المستأجرين (كل Platform Tenant هو حد العزل الأعلى، وتحتَه Group اختياري ثم School كوحدة تشغيلية) لإدارة المدرسة بالكامل: الإعدادات الأكاديمية، القبول والتسجيل، الطلاب وأولياء الأمور، الموظفين، الحضور، الدرجات والشهادات، المالية والرواتب، التواصل عبر واتساب، التقارير، والجدول الدراسي. يعمل عبر الويب وتطبيق للهاتف والتابلت.

**المبدأ الأساسي:** كل ما يختلف بين مدرسة وأخرى يُدار من "إعدادات المدرسة" وليس في الكود: المراحل، الشعب، المواد، الدوام، توزيع الدرجات، قواعد النجاح، الرسوم، الخصومات، قواعد الإشعارات.

**خارج النطاق:** الوضع القانوني أو الترخيصي للمدارس. لا يوجد رفع نتائج لأي وزارة أو منصة خارجية.

## 2. المستخدمون والأدوار

كل دور له حساب مستقل. الصلاحيات متفاوتة حسب الدور.

| الدور | الكود | الصلاحيات الأساسية |
|---|---|---|
| مدير المنصة | `platform_admin` | إنشاء المدارس وإدارتها على مستوى المنصة (أحمد) |
| الإدارة | `school_admin` | كل شيء داخل المدرسة، اعتماد الدرجات والتعديلات والخصومات |
| السكرتارية | `secretary` | القبول والتسجيل، بيانات الطلاب وأولياء الأمور، المستندات |
| المحاسب | `accountant` | الرسوم، المدفوعات، الكفالات، المصروفات، الرواتب |
| المعلم | `teacher` | الحضور، إدخال درجات مواده وشعبه، رؤية بيانات أسر طلابه |
| الأخصائي الاجتماعي | `counselor` | الملاحظات السلوكية والاجتماعية |
| مشرف الباص | `bus_supervisor` | كشف طلاب الباص (مرحلة لاحقة) |
| ولي الأمر | `guardian` | متابعة أبنائه: الحضور، الدرجات المعتمدة، الرسوم، الإعلانات |
| الطالب | `student` | قراءة فقط: درجاته المعتمدة، حضوره، جدوله |

**مربي الفصل** ليس دوراً مستقلاً، بل تكليف (`class_teacher_assignment`) لمعلم على شعبة في سنة دراسية. مربي الفصل يرى درجات كل المواد لفصله.

**ملاحظات:**

- ولي الأمر يدخل النظام بنفسه ويستقبل رسائل واتساب أيضاً.
- ولي الأمر قد يكون غير الأب، أو مقيماً خارج مصر، وقد يكون للطالب أكثر من ولي أمر.
- نموذج البيانات يسمح بأكثر من `membership` للمستخدم (مثلاً ولي أمر لأبناء في مدرستين)، لكن الواجهة تعمل بدور واحد نشط في كل جلسة.

### 3.2 نموذج الـ Multi-Tenancy

**القرار النهائي:** قاعدة بيانات مشتركة + schema مشترك، مع حد عزل أعلى هو `Platform Tenant`، وتحته `Group` اختياري، ثم `School` كوحدة تشغيلية.

العلاقات الأساسية:
- `platform_tenants` هو العميل/المؤسسة وأعلى حد لعزل البيانات.
- `groups` تتبع Tenant واحداً، وقد تضم مدرسة واحدة أو عدة مدارس.
- `schools` تتبع Tenant واحداً، وتتبع Group واحداً أو لا تتبع أي Group.
- لا يوجد Cross-Tenant identity/data sharing تلقائي.
- `profiles` يمثل حساباً واحداً داخل Tenant واحد فقط.
- التفويض = `Role + Permission + Scope`. النطاق قد يكون Tenant أو Group أو مدرسة واحدة أو عدة مدارس.
- Platform Admin تابع لمشغل النظام وليس عضواً في Tenant تلقائياً، والوصول إلى بيانات العملاء الحساسة يحتاج صلاحية صريحة وسجلاً تدقيقياً.

**ملكية البيانات:**
- كل جدول Business يحدد صراحةً هل ملكيته `Platform Tenant` أو `Group` أو `School`.
- كل جدول School-level يحتوي `school_id NOT NULL` حتى لو أمكن اشتقاق المدرسة من FK آخر.
- جداول الهوية المشتركة داخل المجموعة (مثل `students`) لا تضاف إليها `school_id` لمجرد سهولة RLS؛ الوصول إليها يثبت عبر علاقاتها المدرسية (خصوصاً `enrollments`).

**RLS:**
- العزل يبدأ دائماً من `platform_tenant_id`.
- بعد ذلك يطبق نطاق المستخدم: Tenant → Group → School.
- لا تعتمد الحماية على `user_school_ids()` وحدها؛ نحتاج دوال صلاحيات مثل `app.can_access_tenant()`, `app.can_access_group()`, `app.can_access_school()` و`app.has_permission()`.
- يجب تنفيذ دوال RLS الحساسة كـ`SECURITY DEFINER` مع `search_path` مضبوط، ومنع recursion في policies.
- Frontend لا يمثل Security Boundary؛ Backend + RLS + DB constraints هي المصدر الفعلي للحماية.

**ملاحظة:** الـsubdomain يحدد سياق المدرسة للواجهة، لكنه لا يمنح أي صلاحية بحد ذاته.

### 3.3 قواعد إلزامية لكل الكود

1. كل جدول School-level: `school_id uuid not null references schools(id)`، وRLS مفعّل، وindex على `school_id`. جداول Tenant/Group/Identity-level تتبع مستوى ملكيتها ولا نضيف لها `school_id` اصطناعياً.
2. كل جدول جديد يُضاف له اختبار pgTAP يثبت أن مستخدم المدرسة (أ) لا يستطيع قراءة أو تعديل بيانات المدرسة (ب).
3. الإعدادات التي تؤثر على الحسابات (توزيع الدرجات، قواعد النجاح، الرسوم) مرتبطة بـ `academic_year_id`. تغيير الإعدادات لا يغيّر نتائج سنوات سابقة.
4. التغييرات الحساسة تُسجَّل في `audit_log` (القيمة القديمة، الجديدة، المستخدم، الوقت، السبب): الدرجات بعد الاعتماد، المدفوعات، الخصومات، الملاحظات الحساسة، الصلاحيات.
5. المبالغ: `numeric(12,2)` بالجنيه المصري. لا حذف لأي سجل مالي؛ التصحيح يكون بقيد عكسي.
6. الوقت: `timestamptz` في قاعدة البيانات، والعرض بتوقيت `Africa/Cairo`.
7. الحذف ناعم (`archived_at`) للطلاب والموظفين وأولياء الأمور.
8. الأسماء رباعية: `first_name`, `father_name`, `grandfather_name`, `family_name`، مع `full_name` محسوب.
9. أرقام الهاتف بصيغة E.164 مع رمز الدولة (+20، +970، +972، وغيرها).
10. الواجهة عربية RTL، لكن كل النصوص في ملفات ترجمة (لا نصوص مكتوبة داخل الكود) لتسهيل إضافة لغات مستقبلاً.
11. الملاحظات الصحية والسلوكية والاجتماعية لها مصفوفة صلاحيات حسب التصنيف والدور.
12. مفتاح `service_role` يُستخدم فقط في FastAPI و n8n، ولا يصل للعميل أبداً. لا أسرار داخل المستودع.
13. الملفات (شهادات الميلاد، الجوازات، الصور) في bucket خاص، والوصول عبر signed URLs قصيرة الصلاحية.
14. كل جدول Business يجب أن يحدد مستوى ملكيته صراحةً: Platform Tenant أو Group أو School؛ لا توجد جداول Business "مشتركة" بلا ملكية واضحة.
15. الـUUID هو المعرف الداخلي الأساسي؛ أكواد الأعمال مثل Tenant Code وGroup Code وSchool Code وEmployee Code منفصلة عنه، مستقرة ولا يعاد استخدامها ضمن نطاقها.
16. `profiles` حساب واحد داخل Platform Tenant، ويمكن أن تكون له memberships متعددة في مدارس مختلفة داخل نفس Tenant. لا يوجد ربط تلقائي للحسابات عبر Platform Tenants.
17. لا يعتمد النظام على hard delete للبيانات التشغيلية المهمة؛ الإغلاق/الأرشفة والتسويات/العكس هي آليات المحافظة على التاريخ.
18. العمليات المركبة تستخدم transactions، والعمليات القابلة لإعادة الإرسال تستخدم idempotency/concurrency protection عند الحاجة.
19. لا توجد تغييرات يدوية على Production schema؛ كل تغيير schema يمر عبر migration جديدة، ولا يتم تعديل migration منفذة.
20. النسخ الاحتياطي واختبار الاسترجاع جزء من Foundation قبل إدخال بيانات حقيقية.

## 4. نموذج البيانات المبدئي — أساس الـERD

هذا القسم يثبت **المنطق** قبل كتابة migrations النهائية. التفاصيل الدقيقة للأعمدة والقيود موجودة في `ERD_CORE_v1.md`، ثم تتحول إلى Data Dictionary وSQL migrations.

### 4.1 Foundation / Tenancy / Identity
- `platform_tenants` — Tenant root، Tenant Code ثابت وفريد على مستوى المنصة، status active/suspended.
- `groups` — Group اختياري داخل Tenant، Group Code فريد داخل Tenant.
- `schools` — School داخل Tenant، School Code فريد داخل Tenant، `group_id` nullable، والاسم ليس Unique عالمياً.
- `system_users` / `platform_admin_assignments` — هوية Platform Admin خارج Tenant membership.
- `profiles` — حساب/شخص واحد داخل Tenant، مرتبط بـ`auth.users`.
- `memberships` — علاقة profile داخل Tenant مع حالة العضوية؛ لا تفترض دوراً واحداً أو مدرسة واحدة.
- `membership_roles` — ربط العضوية بعدة Roles عند الحاجة.
- `membership_scopes` — نطاق التفويض: Tenant / Group / School، ويمكن تكرار الصفوف لتغطية عدة مدارس.
- `roles`, `permissions`, `role_permissions` — Permission catalog + standard/custom roles.
- `audit_log` — سجل تدقيق مركزي غير قابل للحذف من التطبيق.

### 4.2 Academic Foundation
- `academic_years`, `terms` — السنة والفصول، بعدد وأسماء وتواريخ قابلة للإعداد؛ سنة واحدة active لكل School.
- `stages`, `grade_levels`, `sections` — إعداد مستقل لكل School، مع ترتيب وسعة وخصائص الشعبة.
- `subjects`, `grade_subjects` — المواد وربطها بالصفوف.
- `bell_schedules`, `periods`, `holidays` — الدوام والحصص والتقويم.

### 4.3 People / Staff / Students
- `staff` — سجل الموظف على مستوى Tenant، Employee Code فريد داخل Tenant.
- `staff_school_assignments` — تكليف الموظف بمدرسة/مدارس، مع الوظيفة/الحالة.
- `staff_specialties`, `teaching_assignments`, `class_teacher_assignments`.
- `families` — كيان عائلة مستقل ضمن Tenant.
- `students` — هوية الطالب، ليست سجلاً مدرسياً. UUID ثابت عند النقل داخل Group. عند عدم وجود Group، يكون نطاق هوية الـofficial ID على المدرسة المستقلة.
- `enrollments` — العلاقة التشغيلية: Student + School + Academic Year + Grade + Section + status/effective dates.
- `guardians`, `student_guardians` — Guardian account مستقل + علاقة Many-to-Many.
- `student_documents`, `student_notes` — ملفات وملاحظات مع ownership/scope وصلاحيات رؤية دقيقة.
- `section_transfers`, `student_transfers` — تاريخ النقل والموافقات.

### 4.4 Attendance / Assessment / Finance / Communication / Timetable
تبقى الكيانات التشغيلية المذكورة في الخطة، لكن جميعها تلتزم بقاعدة الملكية الصريحة وبقرارات v1:
- Attendance: `student_attendance` يومي فقط، سجل واحد/طالب/مدرسة/تاريخ، present/absent في v1.
- Assessment: `grading_schemes`, `assessment_components`, `scores`, `score_change_requests`, `term_results`, `annual_results`, `promotion_decisions`; لا Overall Average ولا Ranking ولا Resit في v1.
- Finance: `fee_items`, `fee_structures`, `student_invoices`, `installments`, `discount_types`, `student_discounts`, `payments`, `payment_allocations`, `receipts`, `refunds`, `reversals`, `credits` وغيرها وفق القسم 7.13.
- Communication: `message_templates`, `outbound_messages`, `message_deliveries`, `announcements`, `notification_deliveries`.
- Timetable: `timetable_versions`, `timetable_entries`, `timetable_constraints`, `timetable_generation_runs`.

**قاعدة تصميم:** لا يجوز إضافة `school_id` أو `group_id` لجدول إلا إذا كان ذلك يعكس ملكية فعلية أو يسهل RLS مع بقاء الملكية الأساسية واضحة.

- [ ] ولي الأمر يستطيع تغيير رقم هاتفه من التطبيق؛ يعتمد الرقم الجديد مباشرة بعد نجاح OTP دون موافقة المدرسة.

- [ ] عند إضافة ابن إلى الحساب، يقترح النظام المطابقة ويؤكد موظف المدرسة الربط قبل اعتماده.

- [ ] عند فشل تسجيل الدخول عدة مرات: قفل مؤقت + تنبيه ولي الأمر + تنبيه أمني للمدرسة.
- [ ] يمكن فك القفل ذاتياً عبر OTP على الرقم المسجل.

- [ ] ولي الأمر يرى بيانات كل مدرسة مرتبطة بأبنائه: الاسم، العنوان، الهاتف، البريد الإلكتروني وبيانات التواصل المعتمدة.

## 6. أسئلة مفتوحة متبقية — فقط ما يؤثر فعلاً على التنفيذ

بعد جلسة اعتماد القرارات الأساسية، لا توجد أسئلة مفتوحة تمنع Foundation. البنود التالية تفاصيل مرحلة لاحقة ويمكن تنفيذها عند الوصول إلى مرحلتها: 

| # | البند | يؤثر على المرحلة |
|---|---|---|
| 1 | تفاصيل تقارير الجهات الكافلة | 7، 10 |
| 2 | تفاصيل الرواتب: البدلات والخصومات وسياسات الغياب/التأخير | 8 |
| 3 | نسخة قوالب الشهادات الفعلية للمدرسة والروضة | 6 |
| 4 | قرار مزود OCR السحابي/المحلي بعد تقييم الدقة والخصوصية والتكلفة | 4 |
| 5 | تفاصيل الاشتراكات والباقات والفوترة التجارية | 13 |

**محسوم قبل Foundation:** tenancy، RLS ownership، student account، guardian account، daily attendance، no Overall Average/Ranking/Resit in v1. هذه ليست أسئلة مفتوحة.

> لا يجوز استخدام هذا القسم لإعادة فتح قرارات الهوية أو الـtenancy أو الصلاحيات أو RLS أو حساب الطالب أو الحضور أو نموذج النقل التي تم اعتمادها في القسم 7.

## 7. القرارات المعتمدة من جلسة مراجعة المتطلبات — 2026-09-17

### 7.1 الحسابات والعلاقات متعددة المدارس
- المدرسة هي وحدة العزل الأساسية.
- يمكن وجود مجموعة/Organization فوق المدارس؛ المدرسة المستقلة لا تحتاج مجموعة.
- نطاق المستخدم قابل للتخصيص: مدرسة واحدة، عدة مدارس، أو المجموعة كاملة.
- يمكن للمستخدم امتلاك عضويات متعددة ضمن المدارس المصرح بها.
- ولي الأمر حساب واحد لجميع أبنائه داخل المجموعة، مع فصل بيانات كل مدرسة.
- لا يوجد ربط تلقائي بين مدارس خارج المجموعة.
- نقل الطالب داخل المجموعة يحافظ على السجل والبيانات وفق قواعد النقل المعتمدة؛ النقل خارج المجموعة ينشئ سجلاً جديداً يدوياً.
- الحساب الواحد لا يسمح بدفع موحد عبر عدة مدارس؛ كل دفعة مرتبطة بالطالب والمدرسة.

### 7.2 الصلاحيات والبيانات الحساسة
- الصلاحيات مبنية على Role + Permission + Scope، مع إمكانية إنشاء أدوار مخصصة.
- لا يجوز لمدير تفويض صلاحيات تتجاوز نطاقه.
- `export` مستقل عن `read` ولكل نوع بيانات صلاحية تصدير مستقلة.
- بيانات ولي الأمر الأساسية صلاحية واحدة، مع تقييد خاص لرؤية الهاتف حسب إعداد المدرسة.
- المستندات الرسمية منفصلة عن بيانات الطالب الأساسية، مع صلاحيات مستقلة للعرض/التنزيل/الرفع/الاستبدال/التصدير.
- الملاحظات الحساسة لها صلاحيات حسب التصنيف والدور، مع تاريخ إصدارات واستعادة تنشئ إصداراً جديداً.
- إلغاء/أرشفة الملاحظة الحساسة من صلاحية الإدارة، مع سبب إلزامي وسجل تدقيق.

### 7.3 الهوية والطلاب والنقل
- `identity/passport` هو معرف الأعمال عند توفره، والـUUID هو مفتاح قاعدة البيانات.
- الهوية/الجواز اختياريان ويمكن إضافتهما لاحقاً.
- لا يسمح بإنشاء الطالب نفسه مرتين داخل المجموعة دون مسار override خاص بالإدارة العليا مع تدقيق.
- عند الاشتباه بمطابقة طالب موجود، يمنع الإنشاء العادي ويحتاج الأمر لمعالجة إدارية.
- النقل داخل المجموعة يحتاج موافقة المدرسة الحالية والجديدة.
- أثناء النقل يبقى الطالب فعالاً في المدرسة الحالية حتى اكتمال النقل.
- حساب ولي الأمر يبقى نفسه عند النقل، وتُنشأ العلاقة الجديدة بعد اعتماد النقل.

### 7.4 الحضور والتقويم
- v1 يستخدم الحضور اليومي فقط؛ لا يوجد حضور لكل حصة.
- حساب المدرسة هو الجهة التي تسجل وتعدل حضور الطلاب.
- لا يوجد سجل حضور أكثر من مرة للطالب في اليوم نفسه، لكن يمكن تعديل السجل.
- الحالات الأساسية في v1: حاضر/غائب؛ سبب الغياب اختياري.
- أيام العطلات مستبعدة من الحضور تلقائياً، مع إمكانية استثناء دراسي مسجل ومدقق.
- المدرسة تضبط تقويم العطلات وأيام الدوام الأسبوعية.
- حساب نسبة الحضور ودليل المقام (أيام التسجيل الفعلي أو أيام الدراسة) قابل للإعداد.
- الانتقال بين المدارس داخل المجموعة يخلق فترة انتقالية لا تعد غياباً.

### 7.5 التقييم والنتائج
- قوالب التقييم قابلة للتخصيص حسب المدرسة/المرحلة/الصف/المادة والفصل.
- كل مكون قد يملك درجة عظمى ووزناً مستقلين.
- حالات الدرجة منفصلة عن القيمة الرقمية: صفر فعلي، غير مدخل، غائب، وحالات أخرى حسب إعداد المدرسة.
- الدرجة النهائية تقرب لأقرب عدد صحيح، ولا تسمح بدرجة سالبة، وما يتجاوز الحد الأعلى يثبت عند الحد الأعلى.
- v1 لا يدعم Extra Credit أو Resit/Reassessment.
- v1 لا يحسب Overall Average ولا Ranking.
- التقرير النهائي في v1 يعرض درجات المواد وحالة النجاح/الرسوب لكل مادة والتحليلات المسموح بها، دون ترتيب طلاب.
- توجد نقطة تحتاج حسمًا قبل تنفيذ قاعدة النجاح النهائية: الخطة القديمة كانت تربط النجاح بمتوسط إجمالي، بينما القرار اللاحق أوقف حساب المتوسط في v1. يجب عدم تنفيذ قاعدة تعتمد على متوسط إجمالي حتى يُحسم هذا التعارض.
- اعتماد النتائج سنوي، ولا يتم اعتماد السنة مع وجود درجات مطلوبة مفقودة.
- النتائج المعتمدة تظهر تلقائياً لولي الأمر/الطالب وفق الإعدادات، مع إمكانية الحجب عنهم دون حذف داخلي.

### 7.6 الواجبات والأنشطة
- v1: المعلم ينشئ الواجب ويرسل للطلاب/أولياء الأمور؛ لا يوجد تسليم أو تصحيح إلكتروني.
- يمكن للمعلم الإرسال لأي شعبة ضمن نطاقه المصرح.
- المرفقات ملفات وروابط.
- تاريخ الاستحقاق يمكن أن يكون تاريخاً فقط أو تاريخاً ووقتاً.
- بعد الإرسال، التعديل غير الجوهري ممكن؛ التغيير الجوهري يعالج بإلغاء القديم وإنشاء جديد.
- التدفق: مسودة → جاهز للإرسال → إرسال فوري أو مجدول.
- الإرسال المجدول قابل للتعديل قبل التنفيذ، والفشل يعيد المحاولة وفق سياسة نظام ثابتة ثم يسجل الفشل.
- نجاح الإرسال يعني نجاح عملية الإرسال للنظام؛ التسليم الفعلي يتابع في سجل الإشعارات.
- التذكيرات التلقائية غير مدعومة؛ التذكير اليدوي متاح للمعلم.

### 7.7 المالية والخصومات
- الخصومات التلقائية لا تتراكم؛ يطبق أعلى خصم تلقائي وفق الأولوية/القيمة.
- الخصم الإداري المعتمد يتغلب على التلقائي.
- خصم الإخوة يمكن أن يكون على مستوى المدرسة أو المجموعة، ويشمل الإخوة من الأب أو الأم.
- التغير في الخصم يعيد حساب المطالبات غير المدفوعة فقط، ولا يغير المدفوعات السابقة تلقائياً.
- الدفع الجزئي مسموح، والتوزيع الافتراضي على أقدم استحقاق مع إمكانية التعديل.
- الإلغاء/الاسترداد لا يحذف العملية الأصلية؛ يتم بقيد عكسي أو حركة مرتبطة.
- الدفع الزائد يتحول إلى رصيد أو استرداد وفق قرار المحاسب وإجراءات الاعتماد.
- الرصيد لا ينتهي تلقائياً ويمكن ترحيله بين السنوات وفق قواعد المجموعة.
- رقم الإيصال فريد ولا يعاد استخدامه، وتصحيح الخطأ الجوهري ينتج إيصالاً جديداً مع إبقاء القديم.
- OCR للإيصالات يقترح رقم العملية والمبلغ والتاريخ والمطابقة، ولا يعتمد الدفع تلقائياً قبل تأكيد المحاسب.
- أسعار الصرف محفوظة وقت الإدخال ولا تستبدل عند الاعتماد؛ التصحيح يكون بحركة مستقلة.

### 7.8 بوابة ولي الأمر والاتصالات
- وسائل الدخول: OTP عبر WhatsApp وSMS، مع دعم كلمة المرور.
- المدرسة تستطيع إنشاء كلمة المرور وإعادة ضبطها.
- إنشاء حساب ولي الأمر تلقائي أو يدوي.
- نمط أول دخول A/B/C قابل للإعداد على مستوى المدرسة.
- تغيير كلمة المرور ذاتياً متاح.
- تغيير رقم الهاتف ذاتياً متاح ويعتمد بعد OTP مباشرة.
- عدة أولياء أمور لكل طالب، ولكل منهم حساب مستقل ونفس صلاحيات الطالب.
- إضافة/ربط ولي أمر تتم من المدرسة فقط.
- ربط الأبناء المقترح آلياً يحتاج تأكيد موظف المدرسة.
- حماية الحساب: قفل مؤقت + تنبيه ولي الأمر + تنبيه المدرسة، وفك القفل بـOTP.
- ولي الأمر يرى الهاتف وآخر دخول فقط من معلومات الأمان.
- بياناته الشخصية الأساسية تعدلها المدرسة، باستثناء تغيير الهاتف.
- ولي الأمر يرى بيانات أبنائه الأكاديمية والحضور والمالية والإعلانات والواجبات، دون تحميل/طباعة في v1.
- الرسائل للقراءة فقط؛ لا محادثة مباشرة في v1.
- الإشعارات متعددة القنوات، مع إعدادات افتراضية قابلة للتعديل لكل نوع.
- بعض الإشعارات تتطلب تأكيد اطلاع، وإعادة الإرسال يدوية فقط.

### 7.9 نموذج المجموعات والصلاحيات
- [ ] دعم مجموعة/Organization اختيارية فوق المدارس؛ المدرسة المستقلة تبقى مباشرة تحت المنصة.
- [ ] نطاق المستخدم يمكن أن يكون مدرسة واحدة، عدة مدارس، أو المجموعة كاملة.
- [ ] مدير المنصة ينشئ المجموعة والمدارس المستقلة، ومدير المجموعة ينشئ المدارس داخل مجموعته فقط.
- [ ] لا يستطيع أي مدير تفويض صلاحية أو نطاق يتجاوز صلاحياته، ويمكنه فقط تضييق النطاق.
- [ ] الأدوار القياسية قابلة للتخصيص، مع صلاحيات مستقلة للقراءة والتعديل والاعتماد والتصدير.
- [ ] `export` مستقل لكل نوع بيانات: الطلاب، الحضور، الدرجات، المالية، الرواتب، الملاحظات الحساسة، المستندات.
- [ ] مدير المنصة ليس تلقائياً صاحب وصول غير محدود للبيانات الحساسة؛ الوصول الحساس يحتاج صلاحية واضحة وسجل تدقيق.

### 7.10 النقل بين المدارس والطلاب
- [ ] داخل المجموعة: يمكن طلب نقل الطالب، ولا يكتمل إلا بموافقة المدرسة الحالية والجديدة.
- [ ] بيانات الطالب وتاريخه ينتقلان داخل المجموعة مع حفظ provenance (المدرسة الأصلية، المستخدم، الوقت، وغيرها).
- [ ] المدرسة القديمة لا تعدل التاريخ الأصلي بعد النقل؛ المدرسة الجديدة لا تصبح مصدر السجل التاريخي.
- [ ] خارج المجموعة: لا يوجد نقل تلقائي؛ يتم إنشاء سجل جديد يدوياً.
- [ ] عند النقل، يبقى حساب ولي الأمر نفسه وتضاف العلاقة الجديدة بعد اعتماد النقل.
- [ ] المديونية غير المسددة تنتقل كالتزام مرتبط بالأصل، مع حفظ المدرسة الأصلية ومدرسة التحصيل.
- [ ] الأرصدة الدائنة لا تنتقل تلقائياً؛ يختار ولي الأمر النقل أو الاسترداد وفق إجراءات الاعتماد.

### 7.11 الحضور والتقويم — تفاصيل v1
- [ ] سجل واحد للطالب في اليوم؛ لا يوجد حضور لكل حصة.
- [ ] المدرسة فقط تسجل وتعدل حضور الطلاب.
- [ ] حالات v1 الأساسية: حاضر/غائب؛ سبب الغياب اختياري.
- [ ] العطلات وأيام الراحة الأسبوعية تمنع تسجيل الغياب تلقائياً، مع دعم يوم دراسة استثنائي مسجل.
- [ ] المقام في نسبة الحضور قابل للإعداد: أيام التسجيل الفعلي أو أيام الدراسة.
- [ ] فترة الانتقال بين المدارس لا تعد غياباً ولا تدخل في المقام وفق الإعداد.
- [ ] في يوم الدراسة الأول بالمدرسة الجديدة، عدم وجود حضور يعني غياباً.
- [ ] يمكن للمدرسة تحديد سياسة يوم الانسحاب وسياسة ظهور الطالب غير المسجل في كشف الحضور.
- [ ] التعديل بعد الحفظ يسجل القيمة القديمة والجديدة والمستخدم والوقت.

### 7.12 الجدول الدراسي
- [ ] القيود الصارمة لا يمكن تجاوزها؛ التعارض بين معلم/شعبة/غرفة يمنع الحفظ.
- [ ] أوقات عدم توفر المعلم والحد الأقصى للحصص المتتالية قيود قابلة للإعداد، مع استثناءات لكل معلم.
- [ ] مولد الجدول يوازن نصاب المعلمين ويوزع حصص المادة على أكبر عدد ممكن من الأيام، ويدعم الحصص المزدوجة.
- [ ] المدرسة تنشئ قائمة قيود وشروط قبل كل عملية توليد، على مستوى المادة أو الجدول كله.
- [ ] دعم Hard Constraints وSoft Constraints مع أولوية يحددها المستخدم.
- [ ] عند عدم وجود حل: تحليل التعارض، اقتراح القيود المرنة القابلة للتخفيف، ولا يتم تخفيف القيد الصارم تلقائياً.
- [ ] يمكن اعتماد أفضل حل بعد موافقة المستخدم عند تخفيف قيود مرنة.
- [ ] التعديل اليدوي يعيد فحص القيود ويرفض التعارض الصارم.
- [ ] كل توليد أو تعديل جوهري ينشئ نسخة، مع إمكانية rollback.
- [ ] الجدول ينشأ كمسودة ثم يعتمد وينشر؛ أي تعديل بعد النشر يمر بمسودة وفحص واعتماد جديد.
- [ ] لا يوجد ربط بين الجدول والحضور في v1.
- [ ] استيراد aSc XML والتوليد بـOR-Tools يدعمان النسخ المتعددة للجدول.

### 7.13 المالية — القرارات التشغيلية
- [ ] الخصم التلقائي الأعلى قيمة فقط هو المطبق عند وجود عدة خصومات تلقائية؛ الخصم الإداري المعتمد يتغلب عليها.
- [ ] خصم الإخوة يشمل الإخوة من الأب أو الأم، ويمكن أن يكون نطاقه المدرسة أو المجموعة، ويحتسب الطلاب النشطين فقط.
- [ ] انسحاب الأخ يعيد الحساب من تاريخ الانسحاب، وإعادة التسجيل تعيد الخصم من تاريخ العودة.
- [ ] الخصم الإداري ثابت المدة ويمكن أن يكون نسبة أو مبلغاً؛ النسبة يعاد حسابها إذا تغيرت الرسوم.
- [ ] التزام الرسوم وخطة الدفع منفصلان؛ يمكن تعديل الاستحقاقات غير المدفوعة، أما عند وجود مدفوعات فتغلق الخطة القديمة وتنشأ خطة جديدة مرتبطة.
- [ ] تاريخ الاستحقاق الأصلي لا يُمحى عند التأجيل؛ يحتفظ بالنص الأصلي والتاريخ الجديد وسبب ومقدم/معتمد الطلب.
- [ ] لا توجد غرامات تأخير في v1؛ فقط حالة متأخر.
- [ ] الدفع الجزئي مسموح، والتوزيع الافتراضي أقدم استحقاق أولاً، مع إمكانية إعادة التوزيع مع حفظ التاريخ.
- [ ] الدفع الزائد يتحول إلى رصيد أو استرداد؛ الاسترداد يحتاج اعتماد المدير.
- [ ] الرصيد لا تنتهي صلاحيته، ويمكن ترحيله بين السنوات؛ الاستخدام يتطلب تخصيصاً/تأكيداً ولا يخصم تلقائياً.
- [ ] إلغاء الالتزام المالي لا يحذف السجل؛ يعطى حالة ملغى وسبب ومستخدم ووقت، وإعادة التفعيل تنشئ التزاماً جديداً مرتبطاً.
- [ ] السنة الجديدة ترحل الديون القديمة كالتزام مستقل مرتبط بالأصل، مع إمكانية تجميعها في مطالبة تحصيل واحدة دون فقدان الهوية الأصلية.
- [ ] السداد الإلكتروني يحتاج مرجعاً خارجياً، وتكرار المرجع ممنوع إلا override إداري مدقق.

## 10. Implementation Lock — 2026-09-22

قبل بدء migrations، تعتبر القرارات التالية مقفلة: 

1. `Platform Tenant → Group(optional) → School` هو التسلسل الرسمي للملكية والعزل.
2. Platform Admin خارج Tenant membership، وله نموذج هوية/تفويض منفصل.
3. `profiles` داخل Tenant واحد؛ لا يوجد cross-tenant profile sharing. ويُفرض ذلك بـ`UNIQUE (profiles.auth_user_id)` عالمياً (قرار O1): نفس Auth User لا يملك profile في Tenantين، وهو شرط حتمية `app.current_tenant_id()`.
4. التفويض `Role + Permission + Scope`، مع `membership_roles` و`membership_scopes` كنموذج مرجعي.
5. `students` هوية شخص، و`enrollments` هي العلاقة المدرسية/السنة؛ لا يوضع `school_id` على `students` لمجرد RLS.
6. RLS يجب أن يثبت Tenant isolation أولاً ثم Group/School scope، وذلك حصراً عبر طبقة التفويض الموحدة `app.can_access_tenant()` / `app.can_access_group()` / `app.can_access_school()` + `app.has_permission()`. لا تُكتب أي policy تستعلم من `memberships` أو `app.user_school_ids()` مباشرة، ولا يُشتق الوصول من تطابق `platform_tenant_id` وحده.
7. كل School-level table يحمل `school_id NOT NULL`.
8. `read` و`export` صلاحيتان منفصلتان.
9. العمليات الحساسة audit + transaction + concurrency protection حسب الحاجة.
10. ERD Core في `ERD_CORE_v1.md` هو نقطة الانطلاق للمراجعة التالية، ثم Data Dictionary ثم Authorization Matrix ثم SQL migrations.

**الخطوة التالية:** اعتماد ERD Core، ثم تحويله إلى Data Dictionary وAuthorization Matrix وRLS policies واختبارات pgTAP قبل تنفيذ أي وحدة تشغيلية.
